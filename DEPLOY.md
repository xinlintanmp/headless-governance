# Deploying the governance agent

Render is assumed below. Railway and Fly.io work the same way — any host that
runs a **container**, not serverless functions. Vercel cannot run this: the
Agent SDK spawns a ~330MB `claude` binary per session and holds state between
requests.

## Before you start

- A GitHub repo with this code pushed.
- A Mixpanel service account with access to your project and workspace.
- An Anthropic API key.
- A password you choose for the app.

## 1. Check it runs locally with auth on

```bash
APP_PASSWORD=some-test-password COOKIE_SECURE=0 \
  uvicorn server:app --port 8000
```

Open http://localhost:8000 — you should get the login page. `COOKIE_SECURE=0`
is only for local HTTP; in production it must stay `1` so the cookie is only
sent over HTTPS.

## 2. Check the image builds

```bash
docker build -t governance .
docker run --rm -p 8000:8000 --env-file .env -e APP_PASSWORD=test governance
```

The image is roughly 600MB–1GB, mostly the bundled `claude` binary. That is
expected.

## 3. Create the Render service

1. Render dashboard → **New** → **Web Service** → connect your repo.
2. Runtime: **Docker**. Render reads `render.yaml` and the `Dockerfile`.
3. Instance type: **Starter or larger**. Each active browser session spawns a
   `claude` process; the free tier's 512MB will not hold more than one, and
   free instances sleep when idle.

## 4. Set the environment variables

In the Render dashboard, under **Environment**. Never commit these.

| Variable | Value |
|---|---|
| `MP_PROJECT_ID` | your numeric project id |
| `MP_WORKSPACE_ID` | your numeric workspace id |
| `MP_USERNAME` | Mixpanel service account username |
| `MP_SECRET` | Mixpanel service account secret |
| `ANTHROPIC_API_KEY` | your Anthropic key |
| `APP_PASSWORD` | the shared password for the app |
| `SESSION_SECRET` | generated by Render — leave it alone |
| `GOVERNANCE_MODEL` | `claude-sonnet-5` |
| `MAX_SESSIONS` | `10` |
| `COOKIE_SECURE` | `1` |

**If `APP_PASSWORD` is unset the app runs with no authentication at all.**
Startup logs say which mode it is in; check the log line after deploying.

## 5. Deploy and verify

Render builds and gives you a URL. Then:

```bash
curl https://your-app.onrender.com/healthz          # {"status":"ok"}
curl -i https://your-app.onrender.com/api/status    # 401 — auth is on
```

If `/api/status` returns 200 without a login, stop and set `APP_PASSWORD`.

Open the URL, sign in, and ask a read-only question first.

## 6. Test a write before trusting it

Ask it to set a description on a **throwaway event**. The approval panel must
appear, and denying must leave Mixpanel unchanged. Only then use it on events
that matter.

## Operational notes

**Sessions.** One `ClaudeSDKClient` per logged-in browser, evicted after an
hour idle. `MAX_SESSIONS` caps concurrency; past it, new users get a 503. Each
session is a subprocess, so raise the instance size before raising the cap.

**Memory is shared.** `remember` writes to the project's Business Context, so
every user of the app and everyone in Mixpanel sees it. Writes are
read-modify-write against a delimited block and never touch the rest of your
context, but they are still team-visible and gated by approval.

**Cost.** Every question is at least two inference calls, and audits are many
more. `GOVERNANCE_MODEL` is the lever; per-turn cost shows in the UI.

**Logs.** Render's log stream shows each request and any tool errors. The
startup banner reports project, workspace, context size, memory entries and
auth mode.

## What this setup does not give you

- **No identity.** One shared password means the audit trail cannot say *who*
  approved a Lexicon write. If that matters, replace `auth.py` with OAuth
  restricted to your domain.
- **No rate limiting.** Anyone with the password can spend your API budget.
- **No audit log.** Writes are approved in the browser and then gone; nothing
  records them beyond Mixpanel's own definition history.
